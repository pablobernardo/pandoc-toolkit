# Add a generic multi-volume book example driven by one adapter
Branch: `feat/book-kit-example`; scope: `examples/book-kit/`, one row in `docs/usage.md` and this feature document. No toolkit change of any kind: nothing in `schemas/`, `scripts/`, `tests/`, `templates/` or `VERSION`.
Why it is one slice over the review budget: the example only proves the pattern if the adapter, both project shapes, the README and the usage row land together, because its claim is that ONE adapter renders BOTH shapes.

## Specs

- S1: "vamos a hacer tu propuesta creo que es lo mejor que creemos el ejemplo perfecto uno de un libro normal y otro para generar una serie o adaptarlo para que acepte las dos opciones? como lo ves?" The maintainer approved building the second example as a pair: one normal book and one series, adapted so one implementation accepts both options.
- S2: A book project is a directory with an optional `series.yaml` and one or more volumes. `series.yaml` holds shared facts (`collection`, `author`, `publisher`, `rights`, `language`) and an ordered `volumes` list of volume directory names. When it is absent the project is a single volume: the project directory itself, with its own `manifest.yaml`.
- S3: `manifest.yaml` per volume: `title`, `subtitle`, `isbn`, `date`, `chapter_start` (optional integer; the first chapter of the volume gets that number), `front_matter` and `back_matter` as ordered maps of logical name to an entry, `chapters` as an ordered list or `ordered: true`, and `language`/`author`/`publisher`/`rights` overrides. The adapter merges series defaults under the volume overrides.
- S4: An entry is either a path string or a map with `file`, `print` (default true) and `optional` (default false). A declared entry whose printable file is missing FAILS with the volume, the logical name and the path in the message; `optional: true` skips it with a warning instead; `print: false` excludes it from the PDF silently.
- S5: The adapter GENERATES the mode switches; content files carry no LaTeX markers. It writes a temporary markdown file before the chapters containing `\mainmatter` plus, when `chapter_start` is set, `\setcounter{chapter}{N-1}`; and one before the back matter containing `\appendix`. Generated files live in the run output, never inside the content directories.
- S6: The adapter is `examples/book-kit/build.py`: executable, `python3`, reads YAML with PyYAML when importable and otherwise falls back to `ruby -ryaml -rjson` over a subprocess with `YAML.safe_load` (mirroring the toolkit's own fallback), discovers the shape, writes one `pdf.config.yaml` per volume into the output directory, invokes `bin/pandoc-pdf render` for each, prints a per-volume summary, has no absolute paths, no network, and works from any working directory.
- S7: The two projects are `examples/book-kit/single/` (no `series.yaml`; three zero-padded chapters, front and back matter) and `examples/book-kit/series/` (two volumes; `volume-2` sets `chapter_start` so its numbering continues from `volume-1`; one volume carries a `print: false` entry and the other an `optional: true` entry whose file is absent, so both rules are exercised rather than described).
- S8: The adapter references the existing `examples/book/templates/book.tex` from the generated `pandoc.template` with a path relative to each project's `base_dir` (the example may point at its sibling directory). The README states that a real consumer copies the template into its own repository.
- S9: No client data, no real ISBN, English artifacts, and no absolute paths (`scripts/check-docs.py` rejects home paths). `templates/book.tex` (the untracked local file at the repository root), `templates/default.tex`, `schemas/`, `scripts/`, `tests/`, `VERSION` and `CHANGELOG.md` are never read, added, modified or deleted.
