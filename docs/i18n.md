# CLI i18n — strategy and contribution guide

This guide describes how the toolkit internationalises its messages without
breaking the CLI contract, keeping security and testability.

## Shared runtime

The current design has two runtimes over the same catalogs:

- **Bash**: `scripts/i18n.sh` is the shared i18n runtime for the bash entry
  points (`bin/pandoc-pdf` and `scripts/bootstrap.sh`). It is sourced, never
  executed. It resolves the language through a single precedence chain,
  loads the catalog once per process (one dump of the JSON catalog), and
  translates with pure bash parameter expansion, so each message lookup costs
  no subprocess. Both entry points therefore share one precedence chain.
- **Python**: `scripts/i18n_runtime.py` serves the Python scripts
  (`preflight.py`, `validate-config.py`, `render-native.py`,
  `prepare-emojis.py`, `check-i18n.py`) with the same catalogs.

Catalogs live in `i18n/locales/*.json` — currently 4 locales (`en`, `es`,
`gl`, `pt`) with 157 keys each — and are validated by
`scripts/check-i18n.py`.

## Goal

- Support multiple languages for CLI and runtime script messages.
- Make adding a new language trivial.
- Keep stability of exit codes, flags, and command semantics.

## Principles

1. **Stable CLI contract**: i18n does not change exit codes or command
   structure.
2. **Key-based catalogs**: never hardcode new texts at runtime.
3. **Secure by default**: the locale is resolved only against the toolkit's
   supported catalogs, with no dynamic loading of arbitrary paths.
4. **Placeholder parity** between languages.

## Language resolution

The bash runtime (`scripts/i18n.sh`) resolves the language in this order:

1. Explicit argument (when the caller passes one).
2. `PANDOC_PDF_LANG` (explicit).
3. Project env file (`.pandoc-pdf.env` next to the toolkit root; overridable
   via `PROJECT_ENV_FILE`).
4. Global toolkit config (`~/.config/pandoc-pdf/config.env`; overridable via
   `GLOBAL_ENV_FILE`).
5. `LC_ALL`, then `LANG`.
6. Fallback: `en`.

The Python runtime (`scripts/i18n_runtime.py`) resolves in this order:
`PANDOC_PDF_LANG`, then `LC_ALL`, then `LANG`, then fallback `en` (it does not
read the env files).

CLI support commands:

- `pandoc-pdf locale show` — shows the effective language and its source.
- `pandoc-pdf locale set <lang>` — saves the global per-user language.
- `pandoc-pdf locale set --project <lang>` — saves the language in
  `.pandoc-pdf.env`.

Normalisation:

- accept `es`, `en`, `pt-BR` (BCP-47); suffixes such as `es_ES.UTF-8@euro`
  are stripped.
- for internal resolution, map to supported locales (e.g. `es-AR` -> `es`).
- an unsupported locale falls back to `en`.

## Structure

```text
i18n/
  locales/
    en.json
    es.json
    pt.json
    gl.json
  schema/
    messages.schema.json
```

Catalog format (example):

```json
{
  "cli.error.unknown_command": "Unknown command: {command}",
  "doctor.ok": "Doctor OK: dependencies available"
}
```

The reference catalog for validation is `es.json`: every other locale must
have exactly the same keys.

## Documentation sections per language code

For the i18n technical guide, use a single document (`docs/i18n.md`) with
sections per locale:

- `## Locale: es`
- `## Locale: en`
- `## How to add a new locale`

For end-user documentation, keep a single version until full localisation is
needed. When necessary, migrate to a dedicated tree:

```text
docs/es/
docs/en/
```

## How to add a new language

PR checklist:

1. Create `i18n/locales/<locale>.json`.
2. Copy all base keys from the reference catalog (`es.json`).
3. Translate values without altering keys.
4. Verify placeholder parity (`{name}`, `{path}`, etc.).
5. Add/update catalog coverage tests.
6. Validate CLI smoke tests with `PANDOC_PDF_LANG=<locale>`.
7. Document the locale in this guide.

## Test strategy

Mandatory minimums (enforced in `tests/run.sh`):

1. **Completeness**: all locales have the same keys (`scripts/check-i18n.py`).
2. **Placeholder parity**: placeholders identical per key across locales
   (`scripts/check-i18n.py`).
3. **Locale policy**: invalid locales do not load external catalogs.
4. **Fallback**: an unsupported locale falls back to the default language
   (`en`).
5. **CLI smoke**: representative messages in the active locales
   (`en`, `es`, `pt`, `gl`).

### Known limitation of `check-i18n.py`

`scripts/check-i18n.py` validates catalogs only against each other: key parity
across locales, value types, and placeholder parity. It does **not** check
whether a key is actually used by the code, nor whether a code-referenced key
exists in the catalogs. Stale or missing keys can therefore only be caught by
review and the CLI smoke tests, not by this validator.

## Security requirements

1. Do not build catalog paths from unvalidated input.
2. Resolve the locale only against the toolkit's supported catalogs.
3. Do not use `eval` or executable templates for interpolation.
4. Load catalogs with a safe parser and schema validation.
5. Keep catalogs reasonably sized to avoid abuse.
